AVM is an open and collaborative knowledge graph platform for teams and communities to bridge the gap between your business knowledge and your disparate data silos by easily developing innovative knowledge graph solutions that self-validate and integrate into your complex data systems. This API Guide provides detailed information on how to use the AVM REST API.

Accessing the Swagger Documentation

Every installation of AVM provides Swagger Documentation for the full suite of AVM REST APIs. This documentation is provided as a standard Swagger YAML file as well as a fully interactive hosted version. The Swagger YAML file can be downloaded at $AVM_HOST/swagger-ui/mobi-swagger.yaml. To reach the Swagger Documentation UI, navigate to $AVM_HOST/swagger-ui/index.html. For example, in a default deployment these URLs would look like https://localhost:8443/swagger-ui/mobi-swagger.yaml and https://localhost:8443/swagger-ui/index.html, respectively. If the browser session is already logged into AVM, there is no need to click the Authorize button.

Overview

All operations performed by the AVM UI are exposed through the AVM REST API. Below are some overarching principles for using the API:

  • All endpoints are accessible from the base path of $AVM_HOST/mobirest.

  • The majority of the endpoints utilize the JSON-LD (JSON for Linking Data) as the primary format for data exchange. Any JSON-LD data returned will be in the expanded format. Any endpoints that utilize a specialized JSON format or other data formats will be clearly documented.

  • All returned dates will be in the ISO 8601 format.

Authentication

AVM uses Cookie-based Authentication with JWT (JSON Web Tokens) and Basic Authentication for secure access to the API.

  • To obtain a valid authentication token, send a POST request to $AVM_HOST/mobirest/session with your username and password and the response will provide a cookie called mobi_web_token that can be used for subsequent requests.

  • To logout, send a DELETE request to $AVM_HOST/mobirest/session.

  • Basic Authentication support follows all standard practices for HTTP Basic Authentication. Include the username and password in the Authorization header of the request in the format Basic <CREDENTIALS>. The credentials should be the Base64 encoded form of username:password.

For more information on how to use the API, please refer to the Swagger documentation.

Error Handling

Errors returned by the API typically follow a standard structure defined by the RESTError interface as described in the Swagger documentation. The body of the error response will contain the error details in JSON format.

{
  "error": "Error Type or Code",
  "errorMessage": "A human-readable description of the error.",
  "errorDetails": [] // Optional array of detailed error strings
}

Common HTTP Status Codes you will encounter are:

  • 200 OK: Request succeeded.

  • 400 Bad Request: Invalid input or validation failure.

  • 401 Unauthorized: Missing or invalid authentication token.

  • 403 Forbidden: Authenticated user lacks permission for the resource.

  • 404 Not Found: Resource does not exist.

  • 500 Internal Server Error: Server-side error.

Pagination, Sorting, and Filtering

Many "list" endpoints support standard query parameters for pagination and sorting.

  • limit: (Integer) Number of results to return.

  • offset: (Integer) Number of results to skip (0-based).

  • sort: (String) Property IRI to sort by (e.g., <http://purl.org/dc/terms/title>).

  • ascending: (Boolean) true for ascending order, false for descending.

  • searchText: (String) General text search filter.

Responses from these paginated endpoints will include the following response headers:

  • x-total-count: Total number of records matching the query (useful for calculating total pages).

  • link: Links to next/previous pages (RFC 5988 style).

Best Practices Per Endpoint Group

This section provides some generate best practices for the different tagged groups of endpoints as seen in the Swagger documentation.

  • User Management

    • Validation: Validate inputs (email formats, password strength) on the client side before sending them to the API to reduce unnecessary server load and 400 Bad Request errors.

    • Security: Never log or expose user passwords. Ensure all user management traffic happens over HTTPS.

  • SPARQL

    • Request Method: Use POST for SPARQL queries whenever possible. GET requests have URL length limits that complex SPARQL queries easily exceed.

    • Performance: Use the LIMIT clause in your SPARQL queries to prevent fetching massive result sets that can crash the browser or overload the server.

    • Injection Safety: Sanitize any user input injected into SPARQL query strings. Avoid direct string concatenation if possible, or validate inputs strictly to prevent SPARQL injection attacks.

  • Ontologies

    • Large Files: When uploading large ontologies, compress them (e.g., into a .zip file) to reduce network latency and transfer time. The API supports zipped uploads.

    • Caching: Only use clearCache=true when absolutely necessary (e.g., debugging specific inconsistency issues). Clearing the cache degrades performance for subsequent requests as the ontology must be reloaded and reasoned over.

    • In-Progress Commits: Use applyInProgressCommit=true when you want to see the "draft" state of the ontology currently being edited by the user. Use false to see the last persisted state.

  • Shapes Graphs (SHACL)

    • Validation: Use getNodeShapes to retrieve form definitions. This allows you to dynamically build UI forms that comply with the SHACL constraints defined in the graph.

    • Dependencies: When updating a shapes graph, be aware of other records (like Datasets or Workflows) that depend on these shapes for validation or UI generation.

  • Mappings

    • Preview First: Before committing a mapping or performing a full download, use the preview functionality (if available via other endpoints or client-side logic) to verify the mapping produces the expected RDF structure.

  • Merge Requests

    • Duplicate Checks: Before creating a new Merge Request, query existing requests (getRequests) to ensure a request for the same source/target branch and record doesn’t already exist.

    • Descriptive Titles: Encourage descriptive titles and descriptions for Merge Requests to help reviewers understand the context of the changes.

  • Workflows

    • Real-time Monitoring: Do not poll the execution status endpoint frequently. Instead, subscribe to the Server-Sent Events (/sse-stream) to receive real-time updates on workflow activity start/stop events.

    • Log Management: Only fetch full logs when requested by the user. Logs can be large; utilize the preview or specific log file endpoints to save bandwidth.

  • Settings

    • Defaults: Always have a fallback mechanism in your client code if a specific setting is missing or fails to load.

    • Type Safety: Use the correct Setting Type IRI when querying to ensure you retrieve the expected configuration group.

  • Provenance

    • Filtering: Always use the entity or agent filters when querying activities. The unfiltered list can be extremely large and slow to retrieve.

  • Record Permissions

    • Verification: Before attempting to modify a record, check the user’s permissions (often returned in the record metadata or checkable via this endpoint) to enable/disable UI controls appropriately.

  • Server-Sent Events(SSE)

    • Reconnection: Implement automatic reconnection logic with exponential backoff on the client side, as connections can be dropped intermittently.

    • Filtering: The stream sends all events. Filter on the client side based on the event type relevant to your context (e.g., com/mobi/workflows/…​).

Get a Record’s IRI

Many of the Record specific endpoints require the IRI (Internationalized Resource Identifier) of the record as a parameter. This IRI is typically returned when you first create or retrieve a record, and it’s used to uniquely identify that record in the system. There are multiple ways to retrieve these IRIs:

  • Option 1: Copy the IRI via the AVM UI

    1. In the AVM UI, navigate to the Catalog module.

    2. Search for the title of the Record you wish to identify. Hover over the title of the Record and click to copy the Record IRI or click the copy button next to the title.

  • Option 2: Search for the Record via the API This option involves making a search query against all the Records in AVM. This search text could be one of the keywords on the Record or a key phrase in the description or in the title. We also filter the list down to only the Ontology Records.

    1. Execute a GET request to /catalogs/http%3A%2F%2Fmobi.com%2Fcatalog-local/records with the following query parameters to retrieve a JSON-LD array of all the Records that match the search text you provide.

      Parameter Name Value

      type

      The URL-encoded IRI of the type of Record you want to retrieve. Eg. to get Ontology Records, use http%3A%2F%2Fmobi.com%2Fontologies%2Fontology-editor%23OntologyRecord

      searchText

      The text to search for in the Record titles and descriptions.

    2. Find the JSON-LD object for your Ontology Record in the response and copy the value of @id.

Note
 This response will also provide all the other metadata about a Record, such as its description, keywords, last modified date, and so on.

Get a Versioned RDF Record’s Content

Once you have the IRI of a Versioned RDF Record (like an Ontology or Shapes Graph), you can retrieve its content by making a GET request to the endpoint that corresponds to the type of Record you are trying to retrieve. In all endpoints below, replace {ENCODED_RECORD_IRI} with the URL-encoded version of the IRI of the Record you want to retrieve.

  • Ontology Record: /ontologies/{ENCODED_RECORD_IRI}

  • Shapes Graph: /shapes/{ENCODED_RECORD_IRI}

Depending on the version of the Record you are trying to retrieve, the steps vary slightly as detailed below.

Note
 To specify the RDF format for the ontology data, use the format query parameter with one of the following options: jsonld, rdf/xml, or turtle.

  • Option 1: Latest Commit of MASTER No other query parameters are required. Make the call as outlined above.

  • Option 2: Latest Commit on a Particular Branch You will need to get the IRI of the intended Branch

    1. Make a GET call to /catalogs/http%3A%2F%2Fmobi.com%2Fcatalog-local/records/{ENCODED_RECORD_IRI}/branches to retrieve a JSON-LD array of the record branch IRIs.

    2. Find the JSON-LD object of the intended Branch in the response and copy the value of @id.

    3. Provide the encoded Branch IRI as the value of the branchId query parameter in your call to retrieve the Record’s data.

SPARQL Queries

All SPARQL queries in the AVM API are made against the /sparql endpoint, with the path specifying which type of "store" you want to query.

  • repository - Query a repository (i.e. triple store) configured in AVM identified by an IRI in the form https://mobi.solutions/repos/{REPO_ID}

  • dataset-record - Query a Dataset Record identified by its Record IRI

  • ontology-record - Query an Ontology Record identified by its Record IRI

  • shapes-graph-record - Query a Shapes Graph Record identified by its Record IRI

Once you have identified the resource you want to query, you can construct your SPARQL query and make a POST request to the /sparql/{STORE_TYPE}/{IDENTIFIER} endpoint with the query as the request body with the Content-Type header set to application/sparql-query. To change the result format, you can add a Accept header to the request with the following options:

  • SELECT queries

    • application/sparql-results+json

    • text/csv

    • text/tab-separated-values

    • application/vnd.openxmlformats-officedocument.spreadsheetml.sheet (returns an Excel file)

    • application/json

  • CONSTRUCT queries

    • application/ld+json

    • application/rdf+xml

    • text/turtle

    • application/json

To download the results of the query as a file, specify the file name in the fileName query parameter and the desired result format as the fileType query parameter with the following file extension options:

  • SELECT queries

    • json

    • csv

    • tsv

    • xlsx

  • CONSTRUCT queries

    • json

    • xml

    • ttl

Note
 If you are querying a Versioned RDF Record type like an Ontology or Shapes Graph, make sure to include the branchId or commitId query parameters as appropriate to specify the version you want to query. To query the latest Commit on the MASTER branch, you can omit those parameters. To include your user’s in progress changes, use the applyInProgressCommit=true query parameter. You can also optionally include imported data by using the includeImports=true query parameter.

Making Commits to a Versioned RDF Record

Within the AVM versioning system, every Commit to a Versioned RDF Record (such as an Ontology or Shapes Graph) starts as what is called an "In Progress Commit". This is a temporary state that allows you to make changes to the Record without affecting the published version. Once you are satisfied with the changes, you can finalize the changes by turning the In Progress Commit into a final immutable Commit. A user can only have one In Progress Commit per Record at a time.

An In Progress Commit is made up of the additions and deletions to be applied to the Record. This can either be built incrementally or all at once with an "upload changes" action. The workflows for each are described below.

Incremental Updates

Incremental updates are performed via PUT requests against the /catalogs/http%3A%2F%2Fmobi.com%2Fcatalog-local/records/{ENCODED_RECORD_IRI}/in-progress-commit endpoint containing the triples you wish to include as additions and deletions in your Commit. This endpoint will create an In Progress Commit if the requesting user does not already have one and otherwise will simply update the existing In Progress Commit. The request takes URL Encoded Form Data with the following fields

  • additions - A JSON-LD array of the triples to be added to the compiled resource

  • deletions - A JSON-LD array of the triples to be removed from the compiled resource

Repeated PUT requests are additive and will continue to combine the existing additions and deletions associated with the In Progress Commit with the new data provided in the request. To "clear" what is currently within the In Progress Commit, you can make a DELETE request against the same endpoint.

All-at-Once Updates

Performing an "All-at-once" is generally called "Uploading Changes" within the AVM UI. This path does not require you to have made an In Progress Commit ahead of time unlike incremental updates. This functionality is available via a PUT request against the following base URLs for the listed types of Versioned RDF Records:

  • Ontology Records - /mobirest/ontologies/{ENCODED_RECORD_IRI}

  • Shapes Graph Records - /mobirest/shapes-graphs/{ENCODED_RECORD_IRI}

  • Workflow Records - /mobirest/workflows/{ENCODED_RECORD_IRI}

Each endpoint accepts optional query parameters for branchId and commitId to specify the version of the Record’s compiled resource to compare against. The absence of these parameters means it will compare against the head Commit of the MASTER Branch. The new data should be provided via a file field in URL Encoded Form Data.

Note
 All endpoints will throw an error if the user making the request already has an In Progress Commit for the specified Record. You must either commit those changes or discard them before making a new request.

To finalize the changes once they have been uploaded, make a POST request against /mobirest/catalogs/http%3A%2F%2Fmobi.com%2Fcatalog-local/records/{ENCODED_RECORD_IRI}/branches/{ENCODED_BRANCH_IRI}/commits with a message query parameter containing text you would like to associate with the immutable Commit being made.

Merging Branches

A merge between branches is made by making a special commit on the "target" Branch that is linked to the head Commit of the "source" Branch. Performing the merge requires identifying the IRIs of the source Branch and target Branch in question, checking for any conflicts between the version history of the two Branches, and then hitting a dedicated endpoint to create the merge Commit. Conflicts are resolved by inverting the changes you don’t want for each conflicting scenario in the merge Commit delta.

  1. Identifying Branch IRIs - You can either copy the Branch IRIs from the UI, or you can make a REST request to fetch the IRIs from the Branch JSON-LD definitions.

    1. Option 1: Copy the IRI from the UI

      1. In the AVM UI, navigate to the Catalog module.

      2. Search for the title of the Record with the Branches. Click on View for that Record.

      3. In the Record view, click on the Branches tab. Identify the Branches in question and click on their titles to copy the IRI.

    2. Option 2: Fetch the IRI via REST API

      1. Make a GET request to /catalogs/http%3A%2F%2Fmobi.com%2Fcatalog-local/records/{ENCODED_RECORD_IRI}/branches

      2. Search for the JSON object with a http://purl.org/dc/terms/title value matching the Branch in question. Copy the @id value to get the IRI

  2. Checking for Conflicts

  3. Make a GET request to /catalogs/http%3A%2F%2Fmobi.com%2Fcatalog-local/records/{ENCODED_RECORD_IRI}/branches/{ENCODED_BRANCH_IRI}/conflicts with the encoded IRI of the target Branch in the targetId query parameter

  4. If the response is empty, there are no conflicts and you can proceed to Step 3

  5. If the response is not empty for each object in the array, decide whether to keep the additions and deletions listed for the left (i.e. the target Branch) or for the right (i.e. the source Branch). Which ever you choose, take the additions and deletions from the other "side" and keep for Step 3

  6. Creating the Merge Commit

    1. Make a POST request to /catalogs/http%3A%2F%2Fmobi.com%2Fcatalog-local/records/{ENCODED_RECORD_IRI}/branches/{ENCODED_BRANCH_IRI}/conflicts with the encoded IRI of the target Branch in the targetId query parameter. Provide the following URL Encoded Form Data:

      1. conflicts - The exact JSON response you received from Step 2, even if it was empty

      2. additions - The combined deletions from all the identified other "sides" from each conflict

      3. deletions - The combined additions from all the identified other "sides" from each conflict

Creating and Using Workflows

Complete management and execution of Workflows can be accomplished through the AVM UI, but is also possible through the extensive REST API suite. Common flows when maintaining Workflows are described below.

Create a Workflow

To create a workflow, follow the steps below.

  1. Create a file containing the RDF definition of your Workflow. An example file is shown below.

    workflow.ttl
    @prefix owl: <http://www.w3.org/2002/07/owl#>.
@prefix xsd: <http://www.w3.org/2001/XMLSchema#>.
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#>.
@prefix sh: <http://www.w3.org/ns/shacl#>.
@prefix w: <http://mobi.solutions/ontologies/workflows#>.
@prefix : <https://mobi.solutions/test#>.
@base <https://mobi.solutions/test>.

:WorkflowA a w:Workflow ;
    w:hasAction :TestActionA .

:TestActionA a w:TestAction, w:Action ;
    w:testMessage "This is a test." .

  2. Send a POST request to /workflows with the following form data contents. The response from this endpoint will include the IRI of the newly created Workflow Record, which will the unique identifier for your Workflow needed for any further requests.

    Parameter Description

    file

    The required binary RDF file containing your workflow definition

    title

    The required title for the Workflow Record you are creating

    description

    An optional description for the Workflow Record you are creating

    markdown

    An optional markdown overview of the Workflow Record you are creating

    keywords

    An optional list of keywords to associate with the Workflow Record you are creating

  3. Once created, the Workflow Record will appear in the Catalog UI in the application so record metadata and permissions can be adjusted from there.

Update a Workflow Definition

Workflows are managed by Workflow Records, which are types of Versioned RDF Records. This means that all changes to the definition of the Workflow must go through the standard graph-versioning flow in order for the changes to be recognized by the system. Thus, to update the definition of a Workflow, you will need to first create an In Progress Commit with the changes and then commit those changes to the MASTER branch. This can be done by either uploading a new version of the workflow as a file or manually creating an in progress commit with the added and deleted triples. Regardless of which option you choose, you will need to follow steps similar to those below.

  1. Make a GET request to /catalogs/http%3A%2F%2Fmobi.com%2Fcatalog-local/records/{ENCODED_RECORD_IRI}/branches/master where ENCODED_RECORD_IRI is replaced by the URL encoded version of the IRI of the target Workflow Record. Manually Initiate a Workflow Execution

Workflows can be configured with automated triggers that will initiate executions, but a Workflow can always be triggered manually following the steps below.

  1. Send a POST REST request to /workflows/{ENCODED_RECORD_IRI}/executions where ENCODED_RECORD_IRI is replaced by the URL encoded version of the IRI of the target Workflow Record. This will initiate an execution of the target Workflow in an asynchronous process and provide the IRI of the generated w:WorkflowExecutionActivity in the response to be used in subsequent calls to fetch the status and logs.

Creating a Webhook

To create a Webhook Record, follow the steps below.

  1. Create a file containing the RDF definition of your Webhook configuration. An example file is shown below.

    webhook.ttl
    @prefix owl: <http://www.w3.org/2002/07/owl#>.
@prefix xsd: <http://www.w3.org/2001/XMLSchema#>.
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#>.
@prefix sh: <http://www.w3.org/ns/shacl#>.
@prefix web: <https://mobi.solutions/ontologies/webhooks#>.
@prefix : <https://mobi.solutions/test#>.
@base <https://mobi.solutions/test>.

:WebhookConfigurationA a web:WebhookConfiguration ;
    web:url "https://webhook.site/bea4adf7-86e3-4d2c-a4c6-3ad90f28b7cf" ;
    web:httpMethod "GET" ;
    web:eventFilter "(event.topics=com/mobi/catalog/version)" ;
    web:active true .

  2. Send a POST request to /webhooks with the following form data contents. The response from this endpoint will include the IRI of the newly created Webhook Record, which will the unique identifier for your Webhook needed for any further requests.

    Parameter Description

    file

    The required binary RDF file containing your Webhook configuration

    title

    The required title for the Webhook Record you are creating

    description

    An optional description for the Webhook Record you are creating

    markdown

    An optional markdown overview of the Webhook Record you are creating

    keywords

    An optional list of keywords to associate with the Webhook Record you are creating

  3. Once created, the Webhook Record will appear in the Catalog UI in the application so record metadata and permissions can be adjusted from there.
